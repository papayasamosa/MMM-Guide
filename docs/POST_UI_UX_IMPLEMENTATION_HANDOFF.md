### Decision 12 — Event-family-specific lead/lag timing
**Status: IMPLEMENTED BUT NOT FULLY WIRED — this is the most nuanced status in this document, read carefully.**
- `core/named_event_response.py` implements the approved S3 regularised-spline-basis method (chosen via real benchmarking/research, documented in its own decision record).
- **Model-fitting integration is genuinely done and validated**: `core/named_event_fit_inputs.py` (new) reads the governed event registry and builds the design matrix; `core/hierarchical_model.py` and `core/market_specific_model.py` both accept an additive `named_event_fit_inputs` parameter that, when a family opts in via `transformation_method_reference`, adds a real spline-basis `eta` term to the model graph. **Omitting the parameter (the default) adds nothing at all — confirmed byte-for-byte identical to every pre-existing test in `test_hierarchical_model.py`/`test_market_specific_model.py`, which all still pass unchanged.** Validated with a **real `pm.sample` NUTS posterior-recovery test** (`test_named_event_response_recovery_posterior.py`, schedule/manual-only in CI per `.github/workflows/tests.yml`, ~66 minutes locally without a C compiler) against a synthetic DGP with a planted, known event effect — event weeks score reliably higher than non-event weeks, a 90% credible interval covers the planted truth, and a negative control (same frame, no named-event input) produces no event terms. This is a real, statistically validated production behaviour change for any project whose governed event registry opts a family in.
- **Predict/replay is now also implemented at the core level** (this session's final commit, `053ee923`): `predict_mu`, `predict_mu_market_specific`, and `simulate_sequential_outcomes` can now correctly replay a fitted model's `event_coefs_<family>_<market>` contribution when given `named_event_fit_inputs` (built via the new `build_named_event_fit_inputs_for_replay`). `NamedEventReplayNotSupportedError` is now **conditional** — raised only if the fit consumed a named-event term AND the caller does not supply the replay input — rather than an unconditional dead end.
- **What is NOT yet done, and is real, concrete next work**: **no page or application-layer caller (Scenario Planner, `core/optimization.py`, any backtest utility) constructs and passes `named_event_fit_inputs` through yet.** This means: today, if an analyst fits a model whose governed event registry opts a family into the new response structure, the fit itself succeeds and uses the new timing behaviour, but **the moment they try to view curves, run Scenario Planning, backtest, or optimise for that project, they will hit `NamedEventReplayNotSupportedError`** — because the calling code at those sites has not been updated to build and pass the replay input. Closing this requires: (1) finding every call site of `predict_mu`/`predict_mu_market_specific`/`simulate_sequential_outcomes` in `pages/`, `application/`, and `core/optimization.py`; (2) at each one, constructing `named_event_fit_inputs` via `build_named_event_fit_inputs_for_replay` (using the project's own governed event registry, already available via `core.named_events`) and passing it through; (3) testing each site end-to-end. **Do not build a second replay mechanism — the correct one now exists in `core/predict.py`.**
- Also investigated and correctly deferred: real-UK-data recalibration of the event-response priors/windows — the decision record's own text discloses this as a "STARTING default, requires real-data prior-predictive recalibration" caveat, not resolvable without real data.
- **Files:** `core/named_event_response.py`, `core/named_event_fit_inputs.py`, `core/hierarchical_model.py`, `core/market_specific_model.py`, `core/predict.py`, `core/market_specific_predict.py`, `core/sequential_simulation.py`, `.github/workflows/tests.yml` (new schedule/manual-only recovery job + informational PR gate-check job).

## 6. Important architectural decisions already made — do not reopen without new evidence

- **GSA and Net Bill Through are permanently distinct outcome types, never aliases.** GSA = bill-through date; NBT = pulled back to signup date, refunds excluded. 48-month FH LTR horizon; 120-day DNA Cross-sell window. New/Winback/DNA-Cross-sell are the only three segments.
- **Search taxonomy**: Brand/Non-Brand as the two top-level intent groups; Google/Bing as a separate platform axis; PMax/Demand Gen/YouTube are never Paid Search taxonomy values regardless of source system.
- **SEO**: causal role = `mediator_or_capture_efficiency_state` (a real contribution, not diagnostic-only); primary metric = impression-weighted average GSC position transformed via `1/position`; **never** spend-based ROI/ROAS/CPA for SEO.
- **Google Trends is the approved Brand Demand anchor source**, with a fixed loading of 1.0 to a rescaled 0–100 relative index — never presented as an absolute search count.
- **Event families**: gifting → anticipatory (pre-event lead), remembrance → contemporaneous/post_event, promotional → post_event window-bounded. Method: S3 regularised spline basis, unpooled by default per (market, family), sharing one per-family HalfNormal shrinkage scale across markets. Named event dates are always factual — never moved. This is not "reverse adstock" as literal adstock — confirmed absent anywhere in the codebase.
- **Experiment calibration**: `MMM.add_lift_test_measurements` is the approved mechanism *when and if* this codebase's fitting architecture ever builds a `pymc_marketing.MMM` object — not to be improvised around in the meantime.
- **FX**: Finance constant-dollar (annual per-financial-year rate table) is the default governed method; an optional market-rate/API mode exists in the architecture but must never silently override the default; one shared FX policy across historical valuation/reporting/planning/optimisation.
- **Future assumptions**: the system/model must supply anything it can forecast (demand, seasonality, baseline) — the analyst only supplies what they actually control (planned activity, promotions). Value assumptions (LTR, revenue-per-kit) remain explicit, disclosed, analyst-confirmed numbers — never silently reused from history — per the WP2G/`REQ-ECON-003` decision, reconciled with Decision 14 as "one governed average, not per-week granular re-entry," not as "remove the confirmation step."
- **Baseline**: existing static intercept + trend + Fourier seasonality already satisfies the requirement — no new time-varying process needed, an evidence-based conclusion, not a preference-based one. Do not reopen without new validation evidence.
- **Optimiser objective/constraint vocabulary**: five objective kinds (with `maximise_profit` permanently gated pending a profit definition), ten constraint kinds, all wired into the real optimizer. The sequential-kernel *approach* (T1: raw-numerical-form replay of the sequential simulator; O1: plan-window-total objective) is chosen and benchmarked — do not re-litigate this choice, only implement it (§4 item 1).
- **Capacity framework**: one shared, generalised capacity-limit application module (`core.capacity_plan_application`) usable by Scenario Planner, Optimiser, and Search-cap reporting alike — never a duplicate parallel implementation.
- **PathMC remains deferred, not rejected**, until the core MMM/Scenario Planner/Optimiser are fully working per Decision 19's own stated sequencing. No PathMC dependency exists in this repo.
